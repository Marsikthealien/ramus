# Діаграми як код

Створено: 2026-09-07
Формат проєкту: [PROJECT_FORMAT.md](PROJECT_FORMAT.md)
Протокол правки: [AGENT_GUIDE.md](AGENT_GUIDE.md)

Модель описується текстом, збирається командою і малюється в картинку — без
запуску застосунку. Два кроки, обидва в `ramus-core-demo`:

| Крок              | Задача                            | Клас              |
| ----------------- | --------------------------------- | ----------------- |
| опис → проєкт     | `:ramus-core-demo:specToProject`  | `SpecToProject`   |
| проєкт → картинки | `:ramus-core-demo:renderDiagrams` | `ProjectToImages` |

```bash
./gradlew :ramus-core-demo:specToProject \
    -Pspec=docs/examples/order-processing.yaml -Pout=/tmp/Замовлення.ramus
./gradlew :ramus-core-demo:renderDiagrams \
    -Pin=/tmp/Замовлення.ramus -Pout=/tmp/діаграми
```

## 1. Навіщо окремий опис

Проєкт лежить у git текстом, і [правити значення в ньому
безпечно](AGENT_GUIDE.md#1-головне-правило). Створювати сутності — ні:
ідентифікатор є оборотним перетворенням ключа бази, а не довільним рядком, і
вигаданий `id` у файлі не ламає читання — він мовчки вказує в нікуди. Тому
опис моделі не є проєктом і не редагується як проєкт.

Опис читає рушій. Блоки, стрілки й потоки створюються тим самим API, яким їх
створює застосунок, ключі роздають лічильники, а на виході — звичайний проєкт,
який відкривається, редагується мишею й далі живе своїм життям. Опис
одноразовий: він будує модель, а не супроводжує її. Далі модель — джерело
правди, і правиться вона або в застосунку, або у файлах.

## 2. Опис моделі

YAML, той самий вузький діалект, що й у формату проєкту: дублікат ключа —
помилка читання, а не «остання виграла».

```yaml
model: 'Обробка замовлення'      # назва моделі (класифікатора)
name: 'Обробити замовлення'      # назва кореневого блока; типово = model
type: 'idef0'                    # idef0 | dfd | dfds
blocks: [...]                    # блоки діаграми A0
arrows: [...]                    # стрілки діаграми A0
```

Верхній рівень — це й опис кореневого блока: `x`, `y`, `width`, `height`,
`color` тут задають його прямокутник на контекстній діаграмі A-0. Без них блок
стає посередині, 144 на 80 — як у зразкових моделях `dest/doc`.

## 3. Блоки

```yaml
blocks:
- id: 'accept'                   # локальне ім'я; на нього посилаються стрілки
  name: 'Прийняти замовлення'
  x: 90
  y: 70
  width: 150
  height: 90
  color: '#c8e6c9'               # тло
  text-color: '#000000'          # колір напису
  blocks: [...]                  # декомпозиція
  arrows: [...]                  # стрілки на її діаграмі
```

`id` живе тільки в описі: стрілки шукають блок за ним, а в проєкт він не
потрапляє. Він локальний для діаграми — два блоки на різних діаграмах можуть
мати однаковий `id`.

Вкладені `blocks` дають декомпозицію, і так на будь-яку глибину. Номери вузлів
(`A0`, `A1`, `A12`) рахуються з дерева й у описі не задаються.

## 4. Стрілки

```yaml
arrows:
- name: 'Замовлення клієнта'     # назва потоку
  from: 'accept'                 # id блока або 'border' — межа діаграми
  to: 'pack'
  from-side: 'output'
  to-side: 'input'
```

У IDEF0 роль стрілки задає **сторона блока**, до якої причеплений кінець.
Окремого поля «роль» у моделі немає — [розкладку ще не відділено від
семантики](PROJECT_FORMAT.md#17-межі-формату) — тому опис оперує сторонами:

| Значення    | Сторона  | Роль у IDEF0 |
| ----------- | -------- | ------------ |
| `input`     | ліворуч  | вхід         |
| `control`   | зверху   | керування    |
| `output`    | праворуч | вихід        |
| `mechanism` | знизу    | механізм     |

Типово `from-side: output`, `to-side: input` — звичайна стрілка «вихід одного
блока у вхід наступного». Кінець на межі діаграми свою сторону не називає:
він бере її від протилежного кінця, бо вхід заходить зліва, а керування —
згори.

Назва живе в потоці, а не в стрілці, і **один потік обслуговує всі стрілки з
однаковою назвою** — так само, як у застосунку. Тому `'Персонал складу'` на
двох діаграмах — це один потік, і перейменування зачепить обидві стрілки.

Стрілки без `name` теж бувають — це неназваний потік.

`color: '#b03a2e'` фарбує лінію й підпис. Нотація кольору не вимагає, але на
щільній діаграмі він розділяє ролі швидше за розбирання сторін: керування
одним кольором, механізми іншим, основний потік чорним.

### Зворотні зв'язки

Стрілка, що повертається назад, прямим маршрутом пройшла б крізь блоки, які
щойно обійшла. Нотація вимагає для неї обходу, і опис його називає:

```yaml
- name: 'Звільнений інтервал'
  from: 'support'
  to: 'schedule'
  route: 'under'                 # under — «down and under», over — «up and over»
```

`under` — вниз і під усіма блоками діаграми, для зворотного зв'язку за
входом; `over` — вгору й над ними, для зворотного зв'язку за керуванням.

## 5. Контекстна діаграма

Діаграма A-0 містить один блок — усю систему — і лише її зовнішні
інтерфейси. Її стрілки описуються окремо, бо чіпляються не до блоків
декомпозиції, а до кореневого блока:

```yaml
id: 'system'                     # id кореневого блока
context-arrows:
- name: 'Заявка пацієнта на запис'
  from: 'border'
  to: 'system'
- name: 'Регламент запису медичного закладу'
  from: 'border'
  to: 'system'
  to-side: 'control'
- name: 'Підтверджений талон на прийом'
  from: 'system'
  to: 'border'
```

Узгодженість граничних стрілок A-0 і A0 — на авторові опису: генератор їх не
звіряє. Найпростіше тримати назви однаковими — тоді це буде той самий потік.

## 6. Координати

Робоче поле діаграми — **800 на 444** у координатах моделі (`CLIENT_WIDTH` і
`CLIENT_HEIGHT` у `MovingArea`: 800 на 555 мінус верхня й нижня смуги рамки).
Початок — лівий верхній кут, `x` росте праворуч, `y` — вниз.

Блок, що вийшов за ці межі, застосунок намалює поверх рамки. Генератор цього
не перевіряє: вихід за межі буває навмисним.

Кілька стрілок на одному боці блока розносяться рівномірно вздовж нього.

## 7. Малювання

```bash
./gradlew :ramus-core-demo:renderDiagrams -Pin=<проєкт> -Pout=<каталог> \
    [-Pformat=png|svg] [-Psize=1600x1200]
```

Малює `PIDEF0painter` — той самий код, яким застосунок показує діаграму на
екрані й друкує її. Приймає і каталог проєкту, і `.rsf`.

Ім'я файлу — номер вузла й назва: `A0 Обробити замовлення клієнта.png`. Номер
попереду, бо назви блоків у моделі можуть повторюватись, а номер — ні. Якщо в
проєкті кілька моделей, кожна отримує свій підкаталог.

Малюються лише блоки з декомпозицією: у блока без дітей своєї діаграми немає.

`-Psize` задає розмір полотна, від нього рахується масштаб — це різкість
картинки, а не обрізання: діаграма завжди вміщується цілком.

## 8. Що конвеєр гарантує

**Повторюваність.** Той самий опис дає той самий проєкт, байт у байт. Дати
ревізії лишаються порожніми навмисно: крок розкладки ставив би в них поточний
час, і git показував би зміну там, де опис не чіпали. Потрібні дати —
дописуються у файлах проєкту, [правити значення формат
дозволяє](PROJECT_FORMAT.md#14-рецепти-безпечного-редагування).

**Канонічність.** Після складання кожна діаграма проганяється через ту саму
розкладку, якою застосунок малює її на екрані, і зберігається назад. Це той
самий крок «відкрити в застосунку й зберегти», який документація формату
називає остаточною перевіркою — тож наступне збереження в застосунку файлів
не перебудує.

**Перевірність.** Проєкт відкривається штатним шляхом, отже й перевіряється
штатно:

```bash
./gradlew :ramus-core-demo:yamlToRsf -Pin=<проєкт> -Prsf=/tmp/check.rsf
./gradlew :ramus-core-demo:test
```

## 9. Межі

**Маршрут стрілки простий.** Два-три ортогональні відрізки між кінцями, без
обходу перешкод: стрілка може пройти крізь блок, якщо блоки стоять на одній
лінії. Ліки — рознести блоки координатами, як це робиться і в застосунку.

**Розгалужень немає.** Стрілка, що ділиться на дві (`crosspoint`), описом не
задається — тільки з'єднання «кінець до кінця».

**Тунелювання немає.** Стрілку, яка йде на межу діаграми, опис не позначає
тунельною; що вона робить на батьківському рівні, застосунок вирішує сам.

**Одна модель на опис.** Проєкт може містити кілька моделей, генератор
створює одну.

**Підписи розводяться лише вздовж прямовисних стрілок.** Коли підписи
накладаються, зсунути їх можна тільки вздовж власної лінії, інакше підпис
відірветься від стрілки. Для похилих і ламаних маршрутів такого зсуву немає —
там підпис за потреби пересувають мишею в застосунку.

**Опис не читається назад.** Зворотного перетворення «проєкт → опис» немає:
модель, відредагована в застосунку, з описом більше не пов'язана.
